01 / Student experience

Detailed notes are the main surface.

Capture → Transcribe → Organize → Verify → Study from the notes. A short overview can accompany the detailed version; it never replaces it.

BEFORE CLASS

Prepare once

Choose a course, check the microphone, set note depth and see where processing happens. Start only when capture and storage are ready.

DURING CLASS

Keep the substance

Retain definitions, algorithms, worked steps, assumptions and corrections. Show recording, saved audio, transcription and notes as separate states.

AFTER CLASS

Verify and keep

Follow a claim to its exact source, compare suggested edits, finalize available evidence and export readable Markdown with source excerpts.

02 / Selected architecture

Preserve evidence before generating notes.

A modular backend and separate workers share one authoritative data model. Slow inference must never block recording or turn pending audio into a false Saved state.

01 · BROWSERNext.js + TypeScript

AudioWorklet → packaging worker → IndexedDB audio journal.

02 · AUTHORIZED INGESTFastAPI REST / WebSocket

Own capture runs, validate chunks and serve versioned student content.

03 · DURABLE STATESeaweedFS + PostgreSQL

Verified audio objects plus committed metadata, job ledger and outbox.

After storage verification and database commit → acknowledge the matching chunk → release its browser copy.

04 · SCHEDULINGOutbox → Kafka → job claim

Reference-only events. A database reconciler recovers due work when notifications fail.

05 · LOCAL INFERENCEfaster-whisper + Ollama

Versioned speech and topic-wise note proposals. Models and live capacity need qualification.

06 · VALIDATED PUBLICATIONVersions → update journal → UI

Check sources, current attempts and epochs. Preserve student edits; replay missed updates.

Authoritative boundaries

PostgreSQL owns versions, job claims and deletion state. Kafka notifies and replays. Objects hold audio. The browser journal supports recovery within disclosed storage limits.

Honest failure behavior

Keep audio if speech fails, transcript if notes fail, and prior notes if finalization fails. Gaps remain visible. There is no automatic external fallback.

Initial operations: Docker Compose, private service interfaces, persistent volumes, trace IDs and stage/backlog metrics. No initial Valkey, vector index, vision worker or Kubernetes requirement.

04 / Phase 6 implementation sequence

Eight increments. One complete lecture workflow.

All milestones below are planned. Each depends on the previous increment and has testable exit evidence in the roadmap. Fixture preparation can start alongside the foundation.

  1. M01

    Private foundation

    Pin the environment. Add owner sessions, courses, lectures, migrations and real service checks.

  2. M02

    Reliable capture

    Journal, upload, verify and seal audio. Prove interruption recovery and honest saved coverage.

  3. M03

    Transcription & sources

    Run real speech recognition, preserve source versions and allow timestamped inspection/correction.

  4. M04

    Detailed notes & export

    Turn saved evidence into useful study notes. Validate citations and review the content with a human.

  5. M05

    Live updates

    Integrate concurrent speech/notes, resource limits, visible delays and reliable UI replay.

  6. M06

    Protected editing

    Add preferences, overview and version comparisons. Preserve drafts and reject stale suggestions.

  7. M07

    Finalize & manage data

    Account for gaps, retain earlier revisions and complete scoped audio/lecture deletion.

  8. M08

    Full lecture qualification

    Run all 32 acceptance cases, a 45–60 minute lecture, accessibility and real failure drills.

Read dependencies, migration packages and exit criteria

05 / Requirements before release

Keep uncertainty visible and assigned.

Proposed quality gates include 90% key-item coverage, all critical recoverable items, 95% supported reviewed claims and zero unflagged critical errors. They still need human-reviewed calibration.

G01 · Open

Reviewed recordings

Human-reviewed development material and independently annotated held-out lectures.

G02 · Open

Speech & note quality

Technical-term accuracy, source support, useful detail, correction handling and editing effort.

G03 · Open

Usable live performance

A declared configuration measured under simultaneous speech and note generation.

G04 · Open

Real recovery tests

Browser, storage, worker and database faults; edit protection and deletion fences.

G05 · Open

Visual dependence

Determine whether the representative course needs slides or board capture to produce useful notes.

G06 · Open

Complete student workflow

Supported versions, accessibility, privacy, full-lecture outcomes and backup/restore limits.

06 / Expand after the core works

Keep the ambition. Sequence the work.

Useful note extensions

Catch Me Up, Mark Important and a course glossary follow the core path. Bring course materials or visual capture forward only if representative evaluation shows they are necessary for useful notes.

Learning tools

Practice, mastery estimates and personalization follow validated note quality. They are not prerequisites for finalized study notes or export.

Platform demonstrations

Retrieval/vector search, caches, schema registries, the full telemetry suite, Kubernetes, Strimzi, KEDA, GitOps and CDC need a named workload or failure question and measured value. Outbox, ownership, retry and deletion safety are already core.

Next task: M01. Build and verify the private service foundation. The architecture page and passing contract tests are planning evidence, not an implemented recording application.

Multimodal Academic
Learning System

A lecture-first learning platform built around Capture → Understand → Practice → Measure → Personalize. The note-taking experience remains the entry point, while the underlying system builds a course-aware, multimodal learning memory that can explain poorly taught concepts, preserve provenance, and adapt to each student over time.

01 · North Star

What the product is actually doing

The AI is not there to replace thinking. It is there to remove friction, preserve missed information, and help the student re-engage.

1. CaptureAudio, transcript, slides, board photos, course files.
→
2. UnderstandStructure concepts, explain weak instruction, connect prerequisites.
→
3. PracticeGenerate targeted recall, examples, and application questions.
→
4. MeasureTrack evidence of understanding rather than assuming mastery.
→
5. PersonalizeAdapt future notes and reviews to demonstrated strengths and gaps.

Core promise

“Even if a lecture is boring, unclear, or poorly delivered, you should leave with an accurate record and a path to actually understanding it.”

Non-goal

“Ignore class because the AI will do everything.” The system should make catching up easy, not encourage permanent disengagement.

Trust principle

Every generated claim should distinguish lecture-derived content from course-material-derived context and AI-generated explanation.

02 · System Architecture

High-level component map

The system is intentionally modular so transcription, note generation, vision, embeddings, and storage can be swapped independently.

03 · Lecture Pipeline

The lifecycle of one live lecture

Live mode prioritizes responsiveness. Final mode prioritizes accuracy, provenance, and coherence.

Live path

Microphone
  ↓
Audio frames (1–5 s)
  ↓
Voice activity detection
  ↓
Streaming / chunked STT
  ↓
Timestamped transcript segments
  ↓
Topic buffer
  ↓
Note delta generator
  ↓
Live notes UI

Final refinement path

Recorded lecture audio
  ↓
Higher-quality STT pass
  ↓
Transcript correction
  ↓
Topic segmentation
  ↓
Slide / image alignment
  ↓
RAG retrieval
  ↓
Final structured notes
  ↓
Concept extraction + study plan
Important: Do not let arbitrary 30-second windows define the note structure. Maintain a rolling transcript buffer and commit notes around semantic/topic boundaries whenever possible.

Live transcript

Fast, timestamped, editable, and allowed to be imperfect. The student can follow it without waiting.

Live notes

Incremental structured deltas. Never rewrite the whole document every few seconds.

Final notes

Rebuilt after the lecture using the best transcript, visual evidence, retrieved course context, and user note profile.

04 · AI / Model Layer

Provider-agnostic by design

Speech recognition, note generation, vision, and embeddings are separate model roles. The app should never assume one provider handles all four.

interface NoteModelProvider {
  generate(messages, schema, settings)
}

  startSession(config)
  transcribeChunk(audio)

  analyze(image, context)

Default: “Recommended” profile. Advanced users can switch to Fully Local, Cloud, or Custom. Provider-specific model IDs stay under an Advanced panel so the product does not overwhelm normal students.

05 · Course Context & RAG

Course materials become structured memory

Syllabus, slides, homework, readings, and previous lectures should be parsed once and retrieved selectively—not shoved wholesale into every prompt.

UploadSyllabus / PDF / PPT export / homework / notes.
→
ParseExtract text, layout, page numbers, metadata.
→
ChunkSemantic sections, slide boundaries, question blocks.
→
EmbedGenerate vectors and searchable metadata.
→
RetrieveCurrent topic → best matching course context.

Syllabus intelligence

Extract course schedule, exam dates, weighting, topics, policies, office hours, and named resources into structured course metadata.

Slide alignment

Each slide is a retrievable unit. Transcript similarity can infer which slide the professor is currently discussing.

Homework context

Retrieve assignment concepts and referenced topics to explain relevance—without automatically generating submission-ready answers.

Retrieval rule: combine semantic similarity with metadata filters such as course, lecture, document type, slide/page number, and date. Pure cosine similarity alone will eventually return noisy context.

10 · Learning Engine

From notes to evidence of understanding

The learning engine should operate on concepts, not just documents.

Concept pipeline

Final lecture notes
  ↓
Concept extraction
  ↓
Link to existing course concepts
  ↓
Create prerequisite / related edges
  ↓
Generate targeted practice
  ↓
Record attempts
  ↓
Update mastery state
  ↓
Influence next lecture's notes + reviews

Mastery is evidence-based

Use signals such as correctness, question difficulty, response time, hints, repeated errors, review spacing, and application performance. Avoid claiming certainty from a single LLM-generated score.

Start simple: a weighted heuristic is enough for an MVP. Later, you can experiment with Bayesian Knowledge Tracing, Item Response Theory, or other knowledge-tracing methods.

Catch Me Up

Summarize the last missed segment and explicitly connect it to what is happening right now.

8-minute review

A short active-recall session after class focused on newly introduced and emphasized concepts.

Adaptive notes

Condense already-mastered material while expanding unfamiliar concepts, without hiding professor emphasis.

11 · Privacy, Safety & Reliability

Trust is part of the architecture

Lecture recording and academic guidance create privacy and reliability obligations that should be designed in from the beginning.

Privacy modes

Fully Local: local transcription, Ollama, local embeddings, SQLite/local files.

Hybrid: local audio processing with cloud reasoning, or vice versa.

Cloud: easiest setup, strongest models, explicit upload disclosure.

Reliability rules

Keep raw transcript and source links. Display model confidence where useful. Mark AI-added explanations. Let students replay source audio around important notes. Never silently rewrite professor claims as AI facts.

Recording constraint: the product should make recording status obvious and instruct users to follow their institution’s policies and applicable consent laws. Build deletion and retention controls early.
12 · Build Phases

How to build it without creating a monster

Each phase should produce something usable before the next layer is added.

Phase 0 — Foundation

Repo, auth, course/lecture schema, provider interfaces, settings, local development environment, logging.

Exit criterion: user can create a course and lecture and persist basic metadata.

Phase 1 — Reliable Live Capture

Browser microphone capture, audio chunking, faster-whisper or chosen STT, timestamped transcript, WebSocket updates, lecture recording controls.

Exit criterion: 45–60 minute lecture can be transcribed continuously without losing ordering or timestamps.

Phase 2 — Custom Note Engine

Note profiles, structured JSON note deltas, topic buffer, incremental note UI, user-selectable model provider, Ollama support.

Exit criterion: two users can generate noticeably different note styles from the same transcript.

Phase 3 — Course Context / RAG

Document uploads, parsing, chunking, embeddings, vector retrieval, syllabus extraction, slide indexing, provenance.

Exit criterion: note generation can cite relevant course material without loading every file into the prompt.

Phase 4 — Multimodal Capture

Phone QR pairing, image capture, visual classification, board/slide analysis, transcript alignment.

Exit criterion: a board photo can enrich the correct section of lecture notes with source attribution.

Phase 5 — Post-Lecture Learning

Final transcript pass, final note regeneration, concept extraction, “teach this better,” short active-recall sessions.

Exit criterion: every lecture ends with accurate notes plus a targeted review session.

Phase 6 — Measure & Personalize

Mastery events, concept graph, spaced review scheduling, adaptive note density, targeted practice.

Exit criterion: the app changes what it emphasizes based on demonstrated understanding.

Phase 7 — Course Intelligence

Cross-lecture semantic search, exam review mode, “what did professor emphasize?”, concept history, advanced analytics.

Exit criterion: the student can query and study the entire course as one connected knowledge system.

Engineering Rules

Decisions that will save the project later

Store evidence, not just output

Keep raw transcript segments, timestamps, document chunks, and image captures. Generated notes should always be reproducible.

Use schemas for model output

Notes, concepts, provenance, and visual analyses should be structured JSON objects—not freeform blobs that the frontend has to guess how to parse.

Keep provider boundaries clean

No frontend code should know how Ollama, OpenAI, or any STT provider works internally. Route everything through your provider layer.

Prefer modular monolith

One backend repository with strong internal modules is the right tradeoff for the first several phases. Microservices would mostly slow you down.

Kafka Backbone

Events, ordering, consumer groups, retries

Kafka carries domain events and metadata. Large binaries remain in object storage. Lecture-scoped streams use lecture_id as the partition key so ordering is preserved within a lecture while different lectures can process concurrently.

Representative event chain

lecture.started
  ↓
audio.chunk.uploaded
  ↓
audio.chunk.ready
  ↓
transcript.segment.created
  ↓
topic.segment.completed
  ↓
context.retrieved
  ↓
notes.delta.generated
  ↓
notes.block.updated
  ↓
notes.finalized
  ↓
concept.detected
  ↓
practice.generated
  ↓
mastery.updated

Standard event envelope

{
  "event_id": "uuid",
  "event_type": "audio.chunk.ready",
  "schema_version": 1,
  "occurred_at": "...",
  "producer": "realtime-gateway",
  "trace_id": "...",
  "lecture_id": "...",
  "payload": {
    "object_key": "...",
    "sequence": 42,
    "start_ms": 126000,
    "end_ms": 131000
  }
}

Consumer groups

stt-workers, note-workers, vision-workers, document-workers, context-workers, study-workers.

Schema evolution

Protobuf or Avro contracts in Apicurio Registry; compatibility tests protect older consumers.

Idempotency

Assume at-least-once delivery. Use event IDs, deterministic upserts, and unique constraints to prevent duplicate side effects.

DLQ

Bound retries. Permanent failures move to a dead-letter topic whose growth is observable and alertable.

Do not send audio blobs through Kafka. Store the chunk in SeaweedFS and publish only the object key, sequence, timestamps, checksum, and trace context.
Observability

Trace one note from microphone to screen

OpenTelemetry propagates trace context through HTTP, WebSocket work, and Kafka headers so end-to-end latency can be decomposed instead of guessed.

Strimzi

Manage Kafka with Kubernetes CRDs and an operator instead of hand-building broker StatefulSets.

KEDA

Scale worker deployments using Kafka consumer lag. This gives autoscaling a real, measurable trigger.

Helm + Argo CD

Use Helm for packaging after manifests work. Add Argo CD only in a late GitOps phase.

Reliability

Failure handling is part of the demo

The strongest version of this project demonstrates what happens when systems fail rather than only when the happy path works.

Bounded retry

Classify transient vs permanent errors and use exponential backoff before DLQ.

Transactional outbox

Write DB state and an outbox row atomically; publish asynchronously. Debezium CDC can be added later.

Graceful degradation

If RAG fails, preserve lecture-only notes. If note generation fails, preserve transcript. If vision fails, preserve image for retry.

Fault tests

Kill workers, pause Kafka, break Ollama, force DLQs, and verify recovery through metrics and traces.

Revised Build Phases

Infrastructure grows with product capability

Do not boot twenty containers on day one. Each infrastructure addition arrives when there is a concrete workflow to exercise it.

Phase 0 — Foundation + Core Containers

Monorepo, Next.js, FastAPI, Postgres, Valkey, SeaweedFS, single-node Kafka, event envelope, provider interfaces, baseline OpenTelemetry.

Phase 1 — Live Capture + Kafka STT

Browser microphone, audio objects, chunk events, faster-whisper consumer group, ordered transcript, WebSocket delivery, retry + DLQ.

Phase 2 — Custom Note Engine

Ollama, Note Profiles, structured deltas, topic buffering, provenance, Catch Me Up, Mark Important.

Phase 3 — Course RAG + Schemas

Document workers, pgvector, syllabus/slide indexing, metadata-aware retrieval, Apicurio Registry, Protobuf contracts.

Phase 4 — Multimodal Capture

Phone pairing, visual uploads, VLM worker, equation/code/diagram handling, slide alignment.

Phase 5 — Post-Lecture Learning

Final STT, final notes, concepts, Teach This Better, active recall, practice and mastery events.

Phase 6 — Full Observability + Reliability

Prometheus, Grafana, Loki, Tempo, Alertmanager, GlitchTip, outbox, runbooks, failure drills.

Phase 7 — Local Kubernetes

k3d, Helm, Strimzi, probes, persistent volumes, resource requests/limits.

Phase 8 — KEDA + k6

Lag-driven worker autoscaling, concurrency scenarios, p50/p95/p99 benchmark report, resource profiling.

Phase 9 — Optional GitOps / CDC

Argo CD, Debezium, environment overlays, advanced deployment and recovery documentation.

Final architecture rule: if you cannot explain why a tool exists, the failure mode it addresses, or the measurement it improves, remove it. The resume value comes from the engineering reasoning—not the logo count.
